# Asset Summary

個人資産（国内外株式・投資信託・預金/現金・貴金属・不動産・年金・ポイント・暗号資産）のサマリーを表示するローカルWebアプリ。
Crypto-Summary の兄弟アプリで、同じ技術構成（Python / FastAPI / SQLite / vanilla JS + Chart.js、ビルド不要）。
暗号資産はCrypto-Summaryが本体のため、マネーフォワードPDFの暗号資産セクションは取り込みません。
**Crypto-Summary 連携**を設定すると、Crypto-Summary が集計した暗号資産残高がダッシュボード・クラス別・保有一覧に自動で合算されます（下記「Crypto-Summary 連携 / 統合スタック」参照）。手動登録は Crypto-Summary が追跡していない分の補完用です（二重計上に注意）。

## 主な機能

- **マネーフォワードME PDF取込**: 「資産」→「資産内訳」ページをブラウザでPDF保存したものをアップロード → 解析プレビュー（差分表示）→ 確定
- **PDFの定期自動保存（別ツール）**: 資産内訳ページのPDF保存自体を自動化するスタンドアロンツールを同梱（[tools/mf_pdf_autosave](tools/mf_pdf_autosave/README.md)。サーバ機能とは独立にタスクスケジューラ/cronで動く）
- **受信フォルダ（自動取込）**: `data/inbox/` にMFのPDFを置くだけで、起動中のアプリが自動で解析・確定（下記「受信フォルダ」参照）。自動保存ツールの保存先を受信フォルダにすれば、**PDF保存から取込まで全自動**になる
- **証券会社の取引履歴取込**: CSV / TSV / Excel、または画面からコピーした表を貼り付け。**証券会社ごとの書式に合わせる必要はありません** — 列の意味は中身から自動判定し、結果はプレビューで確認・修正できます（下記「取引履歴の取込」参照）
- **手動入力**: 銘柄・保有数・平均取得単価、現物貴金属（グラム）、預金、不動産（評価履歴）、暗号資産。種類ごとのタブに登録済み一覧があり、その場で削除できます
- **評価損益**: 平均取得単価から未実現損益を算出（Crypto-Summaryには無い機能）
- **価格の自動取得**: 国内株・ETF（Yahoo Finance）、投資信託の基準価額（投信協会）、貴金属（先物×為替から円/g換算）、暗号資産（CoinGecko）、FX（Frankfurter/ECB）
- **年金（iDeCo・企業型DC）の自動評価**: 年金の投信を投信協会に連携すると、MFの評価額から口数を逆算（評価額÷基準価額×1万）し、以後は日々の基準価額で自動評価。取込のたびに掛金買付ぶんの口数も追随します（下記「年金の投信も基準価額で自動評価する」参照）
- **推移グラフ**: 過去に遡って評価額推移を表示（初回登録時の保有数で遡及）
- **銘柄の統合（名寄せ）**: 同じファンドが証券会社ごとの表記（例:「eMAXIS Slim全世界株式(オール・カントリー)」と「eMAXIS Slim全世界株オール(8782)」）で二重登録されたとき、1銘柄にまとめられます。投信協会の連携先が同じなら**自動で統合**（起動時・自動判定の適用時・手動連携時）、未連携の銘柄は銘柄管理の「統合」で手動統合。保有一覧は「A証券 他1件」の1行になり、旧名は別名として記憶されて次回の取込から自動で当たります（下記「銘柄の統合」参照）
- **Myポートフォリオ**: 銘柄にタグを付けてテーマ別に集計。オルカンのように複数の資産を含む投信は、タグごとの配分率（%）で按分できるため、タグ別の合計が総額と一致します（重複計上なし）
- **ダッシュボードのカスタマイズ**: 表示するウィジェット（資産推移・クラス構成・タグ別構成・Myポートフォリオ・口座・保有）のオン/オフと並び順を変更でき、資産クラス単位で総資産への算入も切り替えられます

## セットアップ

```powershell
cd "C:\path\to\Asset Summary"
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
```

## 使い方

```powershell
asset-summary web            # http://127.0.0.1:8010
asset-summary web --lan      # LAN内の他端末（スマホ等）からアクセス
asset-summary import "data\マネーフォワード ME.pdf" --as-of 2026-08-04
asset-summary summary
```

## データの置き場所

`data/` ディレクトリ（gitignore済み）に個人データをすべて置く:

- `data/assets.db` — SQLiteデータベース（既定）
- `data/*.pdf` — マネーフォワードME のPDF
- `data/inbox/` — PDFの受信フォルダ（自動取込。処理後は `processed/` / `failed/` へ移動）

**個人資産情報を含むファイル（PDF・DB）は絶対にコミットしないこと。** `.gitignore` で保護済み。

## 受信フォルダ（PDFの自動取込）

Webアプリの起動中、`data/inbox/`（初回起動時に自動作成）を既定30秒間隔で監視し、
置かれたPDFを自動で解析・取込します。Docker でも同じ場所（ホストの `./data/inbox`）です。
Syncthing 等で同期しているフォルダを `AS_MF_INBOX_DIR` に指定すれば、
スマホや別PCで保存したPDFを置くだけの運用にできます。
[tools/mf_pdf_autosave](tools/mf_pdf_autosave/README.md) の保存先（`-OutDir`）をこのフォルダにすれば、
**PDFの保存から取込まで全自動**になります（下記「マネーフォワードME PDFの自動保存」参照）。

- 取込内容は Web UI でプレビューをそのまま確定した場合と同じ:
  暗号資産以外の全セクションを取込、低信頼マッチの行は除外（件数を通知）、
  PDFに無くなった既存ロットはゼロ化（＝売却扱い。そのセクションがPDFにある場合のみ）
- 基準日はPDFの作成日（メタデータ）、無ければファイルの更新日
- 検算NG（資産総額・セクション合計の不一致）や解析不能のPDFは**自動確定しない** —
  `data/inbox/failed/` へ移動するので、画面から手動で取り込む
- 処理済みのPDF（取込済みの同一内容を含む）は `data/inbox/processed/` へ移動
- 書き込み途中のファイルを読まないよう、2回のスキャンで内容が変わらないことを
  確認してから取り込む（設置から反映まで最大で監視間隔の2倍）。
  取込ページの「今すぐスキャン」で待ちを省略できる
- 直近の処理結果は「取込」ページの受信フォルダカードに表示（確定分は取込履歴にも残る）

| 環境変数 | 意味 |
|---|---|
| `AS_MF_INBOX_DIR` | 監視フォルダ。空なら `data/inbox`、`off` で機能無効 |
| `AS_MF_INBOX_POLL` | スキャン間隔（秒、既定 30） |

## 取引履歴の取込

「取込」ページの**取引履歴**タブから、証券会社からダウンロードした取引履歴を取り込めます。
証券会社ごとのアダプタは持っていません。列の意味は次の 3 つを組み合わせて判定します。

1. 見出しの語彙（約定日 / 受渡日 / 銘柄 / 数量 / 単価 / 約定代金 / 受渡金額 …）
2. 値の形（日付らしさ・数値らしさ・証券コードらしさ。和暦や `(1,234)` 形式の負数も読みます）
3. **すでに登録済みの銘柄・口座と一致するか** — 一致率のいちばん高い列が銘柄列

そのうえで **数量×単価＝約定代金** と **受渡金額−約定代金＝手数料+税額** が成り立つかを検算し、
成り立つ組合せを選びます。これにより、**見出しが無い書式・語彙に無い書式でも列を確定**でき、
投資信託（基準価額が1万口あたり）かどうかも自動で判別されます。

判定結果は取込前に必ず表示され、間違っていれば列の対応をその場で直せます。
確定した対応は見出しの指紋をキーに保存され、次回同じ書式なら自動適用されます
（ただし算術検算は毎回やり直すので、証券会社が列の意味を変えても引きずりません）。

- **口座は必ず指定してください**。取引履歴のファイルには証券会社名が入っていないことがほとんどです
- 銘柄名の表記ゆれ（`架空商事（株）` と `架空商事` 等）は、一度紐付ければ次回から自動で当たります
- 期間が重なるファイルを何度取り込んでも二重計上しません。取込履歴から巻き戻せます

**未対応**: 1 件の取引が複数行に分かれた貼り付け（銘柄名がセル内で改行され、口座区分・数量・
単価が縦に並ぶ形。大和コネクト証券の取引履歴画面など）。行×列の表として読めないため
取り込めません。貼り付けたときはその旨を警告に出します。

対応するなら **HTML を保存してアップロードする**のが本筋です。テキストとして貼り付けると
セル構造が失われますが、HTML なら残っているためです — 受渡日が複数行にまたがるのは
`rowspan`、銘柄コードと銘柄名の区切りは `<br>` として明示されており、推測が要りません。
表をグリッドに直すところまで書けば、その先は既存の判定エンジンがそのまま使えます
（標準ライブラリだけで足り、依存も増えません）。

### 登録済みの銘柄に無いもの

**銘柄は自動で作りません。** 「登録済みに無い」は売却済みとは限らず、マネーフォワードME が
拾っていない口座の保有中銘柄かもしれないためです。勝手に作ると同じ銘柄が別名で二重に増え、
保有が割れます。プレビューの「結びつかなかった銘柄」で銘柄ごとに選びます。

| 選択 | 動作 |
|---|---|
| **取り込まない**（既定） | その銘柄の行を一切取り込まない |
| **＋ 売却済みとして登録** | `inactive` の銘柄を作って取引を紐付ける。保有一覧・総資産には出ず、実現損益と取引履歴だけが残る |
| 既存の銘柄を選ぶ | その銘柄に紐付け、名前を別名として覚える（次回から自動で当たる） |

候補は**価格で裏を取ってから**並べます。取引の約定日・単価をその銘柄の価格履歴と
突き合わせ、一致した候補を先頭に、食い違った候補を末尾に置きます（`✓ 価格一致 3件` /
`✕ 価格が不一致`）。名前がまったく同じでも価格が違えば別銘柄だと分かるためで、
投信の候補を基準価額で確かめる `fund_autolink` と同じ考え方です。価格が手元に無い期間は
「検証できない」として名前の類似度に戻ります（外部へは取りに行きません）。

それでも**既定では選びません**。
`架空商事` と `架空撤退商事` のように名前が似ているだけの別銘柄を自動で選ぶと、
気づかないまま合算されてしまうためです。

「売却済みとして登録」で作る銘柄は、その取引から読み取れる範囲で属性を埋めます
（1万口あたりか否か・建値通貨・銘柄コード）。投信を 1 口あたりで作ると取得原価が
10000 倍ずれるため、ここは数量×単価と金額の突き合わせで決めています。

### 何を記録し、何を無視するか

この取込が扱うのは **保有数と取得原価が動くもの** だけです。現金の出入りは資産の内訳を
変えないので取り込みません（残高はマネーフォワードME 側のスナップショットが持っています）。

| 取引 | 保有数 | 取得原価 | 取込 |
|---|---|---|---|
| 買付・売却 | 動く | 動く | する |
| **再投資** | **増える** | **増える** | する（同じ「分配金」でもこちらは無視できない） |
| 配当・普通分配金 | 動かない | 動かない | 記録のみ（合計を銘柄詳細に表示） |
| 特別分配金（元本払戻金） | 動かない | **減る** | する（元本の払い戻しのため） |
| 株式分割・併合 | 動く | 動かない | する |
| 入庫・出庫（証券の移動） | 動く | — | する |
| **振替入金・出金、源泉徴収、還付** | 動かない | 動かない | **しない**（現金しか動かないため） |

「振替入庫」と「振替入金」は一字しか違いませんが前者は証券、後者は現金なので、
判定では証券側を先に見ています。

### 取得日・取得原価の考え方

証券会社は直近数年分の履歴しか出せないことが多いため、**総量はマネーフォワードMEのスナップショットを正**とし、
取引履歴で説明できる分を**引き算**した残りを「取得日不明の期首ロット」として復元します。

| 表示 | 意味 |
|---|---|
| 全期間 | 取引履歴が保有をすべて説明できている。取得単価は履歴から計算した値を損益に使う |
| 一部期間 | 履歴より前から保有あり。残余の取得原価はMFの平均取得単価から逆算する |
| 原価不明 | 残余があり、MF側にも取得単価が無いため確定できない |
| 不整合 | 履歴の数量がスナップショットと合わない（二重取込・銘柄の誤照合・売却行の欠落） |

**「一部期間」のときの正直な但し書き**: 残余をMFの値から逆算する以上、再計算した平均取得単価は
MFと同じ値になります（近似ではなく恒等式）。この場合に新しく分かるのは **取得日・ロット内訳・実現損益** であって
平均取得単価ではありません。損益計算に反映するのは「全期間」かつロットが1本のときだけです。

一方で、**MFに取得単価が無い保有**（いまは損益計算から丸ごと外れています）は、履歴が全期間を覆えば
初めて損益に載せられます。ここがいちばん実利のある場面です。

なお取得日は、取引履歴が無い銘柄でもマネーフォワードMEのPDFが取り込んだ値を表示します。

## 銘柄の統合（名寄せ）

マネーフォワードMEのPDFは同じファンドを**証券会社ごとの表記**で書くため、複数の金融機関で
同じ銘柄を持っていると「eMAXIS Slim全世界株式(オール・カントリー)」と
「eMAXIS Slim全世界株オール(8782)」のように**別銘柄として二重登録**されることがあります。
保有一覧が2行に割れて「他1件」の合算表示にならないのはこのケースです。

### 投信協会に連携済みなら自動で統合される

投信協会の価格ソース（ISIN:協会コード）が同じ2銘柄は、名前が違っても**同一ファンドだと
確定**できるため、手動操作なしで自動統合されます。タイミングは次の3つです:

- **アプリ起動時** — すでに両方とも連携済みの既存データはここで1つになります
- **「未連携の投信を自動判定」の適用時** — 両方が同じファンドに判定されたらその場で統合
- **設定画面から手動で連携した瞬間** — 連携先がすでに他の銘柄で使われていたら統合

生き残る銘柄は「証券会社コード付きの切り詰め名（例 `…オール(8782)`）より素の名前」を
優先して選びます。属性（資産クラス・通貨・単位）が食い違う組は壊さずに残し、警告を出します。

### 手動で統合する（未連携の銘柄など）

価格ソースを連携していない銘柄は同一性を機械的に確定できないため、手動で統合します。
**管理 → 銘柄一覧 → 「⇆ 統合」**で片方（消したいほう）を選び、統合先を指定すると:

- 保有スナップショット・取引履歴・タグ配分・手動評価額が統合先へ移り、銘柄は1つになります
- 保有一覧・銘柄詳細は他の銘柄と同じく「A証券 他1件」の口座横断表示になります
- 消えた銘柄名は統合先の**別名として記憶**され、次回のPDF/CSV取込から自動で統合先に紐づきます
- 統合先に銘柄コードや価格ソースが未設定なら、統合元の設定を引き継ぎます

誤統合を防ぐため、**資産クラス・通貨・数量の単位・基準価額の単位（1万口あたり等）が同じ**銘柄
どうしだけ統合できます。年金セクション由来の行（取得価額は総額）は投信とデータの持ち方が
違うため統合できません（年金は統合ではなく、下記「年金の投信も基準価額で自動評価する」の
連携で扱います）。統合は取り消せないので、確認ダイアログをよく読んでから実行してください。

### 預金・現金の表示

預金・現金は全行が単一の「現金・預金」銘柄に集約されるため、既定では保有一覧でも
「A銀行 他N件」の1行にまとめて表示します。銀行ごとの残高は行のツールチップ・銘柄詳細・
クラス別/口座別ページで確認できます。銀行ごとに行を分けたい場合は
**設定 → 表示設定 → 「保有一覧で預金・現金を1行にまとめる」**をオフにしてください。

## 年金の投信も基準価額で自動評価する

マネーフォワードMEの年金セクション（iDeCo・企業型DC）には**取得価額と評価額しか無く**、
口数も基準価額も書かれていません。そのため年金の保有は取込時の評価額のまま静止し、
次のPDF取込まで動きませんでした。

しかし年金の中身も投資信託です。**設定 → 価格ソース連携**で年金の銘柄を投信協会の
ファンドに紐づける（「未連携の投信を自動判定」にも年金が並びます）と:

- **口数を評価額から逆算**します: `評価額 ÷ 基準価額 × 10,000 = 口数`。
  整数口で評価額を円未満まで再現できる基準日を探すので、逆算値は口数そのものと
  一致します（例: 5,154,925円 ÷ 35,754円 → 1,441,776口）
- 以後は**口数 × 日々の基準価額**で自動評価され、前日比・評価損益も毎日追随します
- 次回以降のPDF取込では、新しい評価額から**その時点の口数を再逆算**するので、
  掛金の買付で増えた口数にも自動で追随します（取込プレビューの数量にも実口数が出ます）
- 取得価額（拠出額ベースの損益計算）はこれまでどおりMFの値を使います

基準価額の履歴がまだ手元に無い場合など逆算できないときは、従来どおり記載評価額の
静的表示のまま安全に動き、履歴が揃った時点（次回取込・次回起動）で自動的に切り替わります。

### 連携先候補の裏取り（値動き照合）

年金はPDFに基準価額の記載が無いため、通常の投信で使う「基準価額の円単位一致」による
自動確定ができません（照合列が「照合不能」になるのはこのためです）。代わりに、
**MFの取込が2回分以上あれば**、自動判定時に候補ごとの**値動き照合**で裏を取ります:

```
前回の評価額 × 候補ファンドの基準価額騰落率 + 掛金増分（取得価額の差） ≒ 今回の評価額
```

直近最大6期間すべてを説明できた候補は「✓ 値動き一致（N期間）」と表示されて先頭に並び、
説明できない候補は「⚠ 値動き不一致」になります。名前の類似度が低くても値動きが一致する
候補（正式名が大きく略されているケース）は落とさずに提示します。

なお値動き照合は**同じ指数に連動する別ファンドまでは区別できない**ため、名前照合と
合成した1つのスコアや自動確定には使わず、人が選ぶための判断材料に留めています。
仮に誤ったファンドへ連携しても、以後の取込のたびに「評価額を連携先の基準価額で
再現できない」という警告が出るので、後からでも気づけます（正しいファンドなら評価額は
口数×基準価額そのものなので、必ず円未満まで再現できるはずだからです）。

### 連携先の変更・解除

**設定 → 価格ソース連携 → 「連携済みの銘柄を表示（連携先の変更・解除）」**を開くと、
投信協会に連携済みの銘柄（現在の連携先コード付き）が並びます。誤連携に気づいたときは
ここから検索して**別のファンドを選び直す**だけで、年金は新しい基準価額で口数が引き直され、
同じファンドに連携済みの別銘柄があれば自動統合も同様に働きます。**「連携を解除」**すると
評価は取込時の記載評価額に戻ります（保有データは変わりません。年金・現金・ポイントの
解除は「未連携」の警告対象にはならず、元の「価格ソース不要」の状態に戻ります）。

## Crypto-Summary 連携 / 統合スタック

Crypto-Summary の集計（コイン別残高・口座別内訳・評価額推移）を Asset Summary 内に合算表示できます。
フロントエンドは CS を直接呼ばず、すべて AS バックエンド経由（`/api/crypto-summary/*` と既存 API へのマージ）。CS 停止中も AS は警告付きで動き続けます。

### docker なし（開発）

```powershell
# 別ターミナルで Crypto-Summary を起動（シングルユーザーモード）
cd C:\path\to\Crypto-Summary; crypto-summary web        # :8000

# AS 側は接続先を指定して起動
$env:CS_BASE_URL = "http://127.0.0.1:8000"      # サーバー間接続
$env:CS_PUBLIC_URL = "http://localhost:8000"    # 画面のリンク先
asset-summary web                                # :8010
```

リンク先を `localhost` にするのは、CS の Google OAuth リダイレクト URI が
`http://localhost:8000/auth/callback` で登録されているためです。`127.0.0.1` で開くと
別ホスト扱いになり、CS がマルチユーザーのときログインできません。

### docker compose（1コマンドで両方起動）

起動スクリプトを使うのが簡単です。`.env` の作成、Crypto-Summary リポジトリの場所の検出、
CS のログインモードの判定（台帳の有無で自動判別）、サービストークンの生成まで済ませてから
compose を実行し、両方が応答するまで待って URL を出します。2回目以降は `.env` の内容をそのまま使います。

```powershell
.\scripts\start.ps1          # Windows
```

```bash
./scripts/start.sh           # Linux / macOS / Git Bash
```

| オプション | 動作 |
|---|---|
| なし | 起動（`docker compose up -d --build`） |
| `-Down` / `--down` | 停止 |
| `-Check` / `--check` | 設定の確認のみ（起動しない） |
| `-Cloud` / `--cloud` | 公開用構成（`docker-compose.cloud.yml`）で起動 |

素の compose を直接使っても構いません。

```bash
cp .env.example .env   # CS_CONTEXT と CS_SERVICE_TOKEN を設定
docker compose up -d --build
```

- AS: http://localhost:8010 / CS: http://localhost:8000（`127.0.0.1` ではなく `localhost` で開くこと。CS の OAuth リダイレクト URI に合わせるため）
- CS を単独 compose で起動しているとポート 8000 が衝突します。先に CS 側で `docker compose down` してください（スクリプトはこれを検出して名指しで知らせます）
- ログイン無しで手軽に試すなら `.env` に `DATA_DIR=`（空）を書くと CS がシングルユーザーになり、`CS_SERVICE_TOKEN` も `CS_USER_SUB` も不要になります
- PBR クローラー連携が必要な場合は CS リポジトリ側の compose を単独で使ってください（統合 compose には含めていません）

### リバースプロキシの配下に置く（Nginx Proxy Manager 等）

サブドメイン（`https://as.example.com`）でもサブパス（`https://example.com/asset/`）でも動きます。

- 公開 URL を `AS_PUBLIC_URL` に書く。カンマ区切りで複数書けるので、ループバックと公開 URL を並べておけば設定を変えずに両方から使えます
- リダイレクト URI は開いた入口から組み立てられるため、`AS_PUBLIC_URL` に挙げた URL の `/auth/callback` を Google に登録しておけばそれだけで足ります
- TLS はプロキシ側で終端して構いません。コンテナ内はプレーン http に見えますが、`AS_PUBLIC_URL` に https で書いてあればそちらのスキームが使われます
- **サブパスの場合はプロキシで接頭辞を落とさない**こと。nginx なら `proxy_pass http://asset-summary:8010;`（末尾スラッシュなし）。接頭辞は `AS_PUBLIC_URL` のパス部分から決まります（`AS_ROOT_PATH` で明示も可）

```
AS_PUBLIC_URL=https://example.com/asset,http://localhost:8010
```

### クラウド VM（named volume + Google OAuth + TLS）

```bash
# AS と CS を兄弟ディレクトリに clone した VM 上で
cp .env.example .env   # 公開URL・OAuth・CS_SERVICE_TOKEN・AS_ALLOWED_EMAILS を設定
docker compose -f docker-compose.cloud.yml up -d --build
```

- caddy が `AS_HOST` / `CS_HOST` の 2 サブドメインで TLS を終端します（Let's Encrypt 自動取得。DNS と 80/443 開放が前提）
- `AS_ALLOWED_EMAILS` を設定すると AS に Google ログインゲートが付きます（CS と同じ OAuth クライアントを共用。リダイレクト URI は両方登録）
- AS→CS のサーバー間読み取りは `CS_SERVICE_TOKEN`（読み取り専用・管理系や書き込みには使えません）。ログインした人の Google アカウントに対応する CS 台帳が読まれます

### 環境変数（連携まわり）

| 変数 | 意味 |
|---|---|
| `CS_BASE_URL` | CS への server-to-server 接続先（未設定なら連携無効） |
| `CS_PUBLIC_URL` | ブラウザから CS を開くリンク先（省略時 CS_BASE_URL） |
| `CS_SERVICE_TOKEN` | AS⇔CS 共有トークン（CS 側にも同じ値を設定） |
| `CS_USER_SUB` | AS 認証オフ時に読む CS 台帳の Google sub（CS マルチユーザー時のみ） |
| `AS_ALLOWED_EMAILS` | 設定すると Google ログインゲートが有効化 |
| `AS_BASE_URL` / `AS_SECRET_KEY` | OAuth リダイレクト元 / セッション鍵（省略時自動生成） |

### バックアップ（SQLite / WAL）

書き込み中の `.db` を直接コピーしない。`VACUUM INTO` でスナップショットを取る:

```bash
docker compose exec asset-summary python -c "import sqlite3; sqlite3.connect('/data/assets.db').execute(\"VACUUM INTO '/data/backup-assets.db'\")"
docker compose cp asset-summary:/data/backup-assets.db ./backups/
```

## マネーフォワードME PDFの自動保存（定期実行）

毎回手動でPDF印刷する代わりに、[tools/mf_pdf_autosave](tools/mf_pdf_autosave/README.md) で自動化できます。
ヘッドレスブラウザ（Playwright）が口座の一括更新を実行して完了を待ってから、資産内訳ページをブラウザ印刷と同等のPDFとして指定フォルダへ保存します。
ログインは初回に1回だけ手動（ID・パスワードは保存されず、ログイン済みセッションだけを端末内のプロファイルに保持）。Windowsタスクスケジューラ登録スクリプト付き。

```powershell
pip install -r tools\mf_pdf_autosave\requirements.txt
python -m playwright install chromium
python tools\mf_pdf_autosave\mf_pdf_autosave.py --login       # 初回のみ
.\tools\mf_pdf_autosave\register_task.ps1 -OutDir "C:\path\to\Asset Summary\data\mf_pdf" -At 07:30 -Keep 30
```

`-OutDir` を受信フォルダ（`data\inbox`）にすると、起動中のアプリが保存されたPDFを
自動で取り込みます（上記「受信フォルダ」参照。取込後のPDFは `processed/` へ移動されるため、
`-Keep` の世代管理は実質不要になります）。

## ヒント

- マネーフォワードMEをPDF印刷する際、ブラウザの印刷設定で「ヘッダーとフッター」を有効にすると印刷日がPDFに入ります（取込の基準日の参考になります）。mf_pdf_autosave はこれ相当のヘッダ/フッタを自動で付けます
- 投資信託はPDFに銘柄コードが無いため、初回取込後に「設定 → 価格ソース連携」の**「未連携の投信を自動判定」**を実行してください。投信協会の銘柄検索と基準価額の照合（MF記載の基準価額と円単位で一致するか）で自動判定されます。為替ヘッジあり/なし等の紛らわしい亜種も基準価額で正しく区別されます。判定できなかった銘柄のみ手動検索で紐付けます
